X380 Yoga reconstructed autopatcher maintenance library
======================================================

Source integration only. CONFIG_X380_AUTOPATCHER defaults to n and is limited
to BOARD_LENOVO_X380_YOGA. When enabled, the two C files join ramstage. Nothing
registers a boot callback, creates a setup option or starts an operation.
Unreferenced functions may be removed by the linker until a caller is added.
These C interfaces are not a payload ABI or a UEFI protocol implementation.

Interfaces (autopatcher.h)
-------------------------
x380_ap_read/write: bank 0x54..0x57, offset 0..255. Map each logical bank into
two 128-byte EC pages. Bank 0x5c offsets 0..7 reproduce the stock DXE stub:
reads return ff; writes do nothing. Invalid addresses fail without I/O.

x380_ap_snapshot: read 0x54..0x57 then the eight synthetic 0x5c bytes into a
1032-byte caller buffer. Abort on a read error; partial output is possible.

x380_ap_apply_template: explicit destructive maintenance entry. First reads
all 256 bytes of bank 0x57 into the caller's backup buffer, then writes the
original patch template, then reads every byte back and checks it. Any error
stops the operation. completed counts successful transfer returns, not proof
of persistence. Partial writes are possible; there is no automatic rollback.
The caller must preserve the backup; this library does not save it to disk.

x380_ap_native_io: obtain the native transport without touching hardware.
Command 5e: transmit [page,index], receive one byte.
Command 5f: transmit [page,index,value], no response data.
Ports: command/status 66h, data 62h. This is not ordinary EC RAM 80h/81h access.
IBF/OBF waits and stale-output draining have bounded 30 us polling intervals.

The native transport is deliberately not used by the host tests. It has no
internal cross-CPU or SMM arbitration: the maintenance caller must first
ensure exclusive EC access, including firmware/SMM/ACPI users. Calling it
after an OS owns the EC or from an arbitrary payload is not supported here.
It does not remove hardware protection or emulate stock AccessProtection.

Changes from the original binary
--------------------------------
The original performed unchecked writes and always displayed a success
message. This implementation checks errors and verifies the complete bank.
It aborts a failed transaction rather than guessing whether it is safe to
retry an incomplete EC command. The stock EcIoDxe failure recovery and its
SMM/ReadyToBoot dependencies have not been ported.

The meaningless 0x5c writes, hardware-ID/key UI, UEFI protocol installation,
success-message infinite loop and offline BIOS/NVRAM-volume replacement are
not copied. The native coreboot entry points replace that invocation chain.
No minimal SVP-only rewrite is substituted: apply_template retains the exact
256-byte original template, including fields whose meaning is not established.
The template is not safe to apply automatically on every boot.

Evidence
--------
Analyzed project: https://github.com/suds-mcduff/lenovo-bios-autopatcher
BootOption.ffs PE SHA256:
86a3b2079e1e46b104f03d88814a1562f4639dbb874bcb6b3ac8a36af3bd016a
Template: PE RVA 1040h, 256 bytes, SHA256:
dce1a98eb599ac2a68a4b587d575c4ff6905c2d218fd24aad4db0880339aa286

Stock CompalECRfidDxe PE SHA256:
9a586edbb28eae9c2a1d20f2549d65a691b2ff09bec41eaa82e16ef058fe480e
Identical in the analyzed X380 BIOS 1.35 and R0SET57W 1.41 samples.
Read entry 7e4h, write entry 918h, port transaction b7ch.
Bank 57h SVP fields: checksums 02h/03h, pair-state bits at 04h,
two 16-byte records at 10h and 20h. The fixed template zeroes these fields.
This does not establish compatibility with other machines or EC versions.

Validation
----------
Host regression test, from the coreboot source root:
  gcc -std=c11 -Wall -Wextra -Werror -Isrc \
    tests/mainboard/x380-autopatcher-test.c \
    src/mainboard/lenovo/sklkbl_thinkpad/variants/x380_yoga/autopatcher.c \
    -o /tmp/x380-autopatcher-test
  /tmp/x380-autopatcher-test

The fixture tests/data/x380-autopatcher-bank57.hex was extracted directly
from the analyzed PE, independently of the C template initializer.
The same host test is registered with the coreboot unit-test Makefile.
Native transport object compilation is not a hardware test. No real EEPROM
contents, persistence across power loss or complete maintenance UI were tested.
